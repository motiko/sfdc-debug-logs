# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Apex Debugger": a Chrome extension (Manifest V3) for viewing and searching Salesforce Apex debug logs, plus keyboard shortcuts for Salesforce setup pages.

## Repository layout

- `chrome/app/`: the unpacked extension: `manifest.json`, HTML pages (`html/app.html`, `html/options.html`), CSS and images. Its scripts are built from `react/` into `chrome/app/js/build/`.
- `react/`: the single npm package and the source of every script (`react/src`):
  - `src/extension/`: one entry per extension script: `background.ts` (service worker), `shortcuts.ts` (all Salesforce pages), `debug-log-page.ts` (classic log page), `debug-log-list.ts` (classic log list), `class-page.ts` (class and trigger lists), `options.js` (options page, React). `classic-ui.ts` is shared by the three classic-page scripts (not an entry).
  - `src/core/`: modules shared by the entries and the app, so a fix lands in both log views:
    - `salesforce/`: `client.ts` (`createSalesforceClient(request)`: every REST, Tooling and Bulk API 2.0 call), `request.ts` (`createRequest`: the fetch transport, JSON/text responses, one token renewal after a 401), `api-version.ts`.
    - `log/`: `parsing.ts` (log splitting, event types, id splitting, USER_DEBUG parsing and beautifying), `callouts.ts` (CALLOUT_REQUEST/RESPONSE and NAMED_CREDENTIAL_* entries: header and value, Apex objects one field per line, JSON/XML values pretty-printed; only values with 3+ fields, a nested object, JSON or XML get a button, so the two-field `System.HttpRequest[Endpoint=…, Method=…]` and `HttpResponse[Status=OK, StatusCode=200]` stay plain), `values.ts` (the expandable values of both views: USER_DEBUG and callouts), `categories.ts` (event type -> color category), `themes.ts` (the log themes as data), `classic-blocks.ts` (the classic page's line blocks and classes).
    - `page-session.ts` (cookies, session, `pageSalesforce()` client for content scripts, the open-app message), `org-hosts.ts` (`isOrgHost`, `apiHostFor`), `page-shortcuts.ts` (the Salesforce-page shortcut registry, see below), `app-shortcuts.ts` (the app's keys), `shared-appearance.ts` (the color mode mirrored for content scripts), `cached.ts` (a value cached in a Storage with a max age).
  - `src/app.js` and the rest of `src/`: the full-page log viewer (`html/app.html`). `src/options/` is the options page's UI; `src/pages/settings/appearance-settings.js` is shared by the app's Appearance panel and the options page.
- The build output, `chrome/app/js/build/*.js` and `app.css`, is **not committed** (gitignored): run `./build.sh` (installs dependencies if needed; `--watch` rebuilds on save, `--zip` packages `chrome/app`) before loading `chrome/app` unpacked.
- `scripts/`: local dev tooling (test browser launcher, Salesforce login).
- `e2e/`: end-to-end flow against a real org or the offline mock org (see below).

## Build and check commands (run in `react/`)

Use Node 24 (`.nvmrc`).

```bash
npm run build         # build.mjs: one Vite build per entry -> chrome/app/js/build/<entry>.js (+ app.css)
npm run dev           # build.mjs --watch: rebuilds on save, then reload the page or the extension
npm run lint          # ESLint 9 over the whole repository (.js/.mjs in react/, e2e, scripts)
npm run format        # Prettier 3: react/src, e2e, scripts (format:check in CI)
npm run typecheck     # tsc --noEmit
npm test              # Vitest unit tests (vitest run); npx vitest to watch
```

`.github/workflows/ci.yml` runs lint, format:check, typecheck, unit tests and build on pushes to `main` and on pull requests (no Salesforce secrets needed).

The toolchain is Vite (`react/vite.config.mjs`) plus TypeScript for type checking only (`tsconfig.json`, `allowJs`, not strict, `@types/chrome`); new files should be `.ts`. `entries` in `vite.config.mjs` lists every script; `build.mjs` runs one build per entry, because content scripts must be classic scripts and Rolldown's IIFE output takes a single input. So each output is one self-contained classic IIFE (`app` also emits `app.css`) with its own copy of whatever it imports, and it satisfies the extension CSP (`script-src 'self'`: no inline scripts, no eval, no code splitting). `build.mjs` empties `js/build/` first and fails if a script that `manifest.json` loads wasn't built. A new script needs an entry in `entries` and a reference in `manifest.json` or an HTML page. Share code by importing from `src/core`, never through globals. Content scripts write log and org data into Salesforce pages: build such DOM with `textContent` and elements, never `innerHTML` (log text can come from public Sites). Sources keep JSX in `.js` files; a small plugin in `vite.config.mjs` compiles it. Dependencies come from npm; nothing is vendored. The app uses React 19 (function components and hooks only), MUI 9 (`@mui/material`, `@mui/icons-material`, Emotion; style with `sx` or `styled`, import icons by path, e.g. `@mui/icons-material/Home`; v9 removed the `*Outline` icon names, use `*Outlined`, and the deprecated `InputProps`/`PaperProps`/`TransitionProps`: use `slotProps`), Redux Toolkit 2 with react-redux 9 hooks (`useSelector`, `useDispatch`) and `@tanstack/react-virtual`. There is no router (see `hash-route.ts`).

**Formatting and lint.** One Prettier config at the root (`.prettierrc.json`: no semicolons, single quotes, no trailing commas, `arrowParens: avoid`; 120 columns in `e2e/` and `scripts/`). `eslint.config.js` (flat config) lives at the root but loads its plugins from `react/node_modules`, so run ESLint from `react/`. ESLint parses only `.js`/`.mjs`: typescript-eslint doesn't support TypeScript 7, so `.ts` files are checked by `tsc` only.

**Unit tests** (`*.test.ts` next to the code, Node environment, config in `vite.config.mjs`): keep logic testable by putting it in plain modules, like `core/log/parsing.ts`, `core/log/callouts.ts` (on `__fixtures__/callouts.log`), `core/log/themes.ts` (every theme styles every category, legacy names, `debug.css` rules) `core/log/execution-tree.ts` (nesting, self/total time, unbalanced and truncated logs), `pages/logs/utils.ts` (log filters), `pages/logs/actions.ts` (search thunk), `persisted-settings.ts` (reading settings saved by older versions) and `hash-route.ts`, `core/log/log-summary.ts` (fixture `__fixtures__/limits-soql-dml.log`). `core/salesforce/client.test.ts` runs the client against a fake request function (query encoding, debug level reuse, trace flag fallback, trace flags for any target, user and class search, the delete-all job); `core/salesforce/trace-flags.ts` (categories, levels, presets, durations) has its own tests. Fixtures such as `core/log/__fixtures__/anonymous-apex.log` are imported with `?raw` (`chrome/app/css/debug.css?raw` too: `test.css` in `vite.config.mjs` keeps it from being emptied).

## Local Chrome testing

`scripts/chrome-dev.sh [url]` launches an isolated browser with the unpacked `chrome/app` extension. Branded Chrome 137+ ignores `--load-extension`, so the script downloads **Chrome for Testing** (stable) into `.chrome-test/` (gitignored). The profile in `.chrome-test/profile` persists. The DevTools protocol is on port 9222 (override with `CDP_PORT`).

- **Auto-login:** if `.env.local` exists (gitignored; keys in `.env.example`: `SF_USER`, `SF_CLIENT_ID`, `SF_JWT_KEY_FILE` (or `SF_JWT_KEY`), optional `SF_LOGIN_URL`; a second org as `SF_USER_2` etc. is used when the first is near its daily API limit, see `scripts/lib/sf-auth.mjs`) and no URL argument is given, Chrome starts blank and `scripts/sf-login.mjs` logs in with the OAuth 2.0 JWT bearer flow (`scripts/lib/sf-jwt.mjs`: an RS256 assertion signed with `node:crypto`, exchanged at `/services/oauth2/token`; setup in `docs/e2e-jwt-setup.md`) + `frontdoor.jsp`, landing on the Debug Logs page. The session id goes over CDP, not the command line. Rerun it against a running browser with `node scripts/sf-login.mjs [retURL]`. An org without `SF_CLIENT_ID` and a key falls back to the deprecated SOAP `login()` (`SF_PASS`, `SF_TOKEN`; Salesforce retires it in Summer '27) with a warning; `SF_ACCESS_TOKEN` + `SF_INSTANCE_URL` skip the login.
- The script builds the extension if `js/build/` is missing scripts (running `npm ci` in `react/` first if needed). After changing content scripts or the service worker, reload the extension on `chrome://extensions`. Every change needs a rebuild (or `./build.sh --watch` running) first; app changes then only need a page reload.
- **Session token:** the `sid` cookie is HttpOnly on current Salesforce, so content scripts can't read it. `getSession()` in `src/core/page-session.ts` asks the service worker (`getToken` message), whose `getSessionForUrl()` (`src/extension/background.ts`), which reads `sid` with `chrome.cookies` for the org's `my.salesforce.com` host (`apiHostFor()` maps Lightning and `salesforce-setup.com` hosts) and returns `{ token, host }`. It answers only for org hosts (`isOrgHost()`): content scripts also run on public Salesforce Sites under `*.force.com`, which must never get a session. Only if there's no cookie does it fall back to the token saved on the options page (`chrome.storage.local.token`). The React app asks the same way after a 401. The e2e flow saves no token, so it exercises the cookie path.

## End-to-end flow (`e2e/`)

**Offline first.** `cd e2e && npm run test:mock` runs the whole flow against the mock org in `e2e/mock/` (no credentials, no Salesforce API requests); `npm run test:harness` checks the harness itself (and runs `scripts/lib/*.test.mjs`; `npm run test:login` runs only the login tests, without Chrome); `npm run ux-audit -- --mock` (or `ux-audit:mock`) runs the UX audit against it (its `callouts` view, mock only, captures a callout log collapsed and expanded in both log views). Use the mock for development and only run against the real org to confirm: the dev org's daily API limit is shared by every run and every developer. The mock (`mock/server.mjs`) is an HTTPS server on 127.0.0.1 with a self-signed certificate (made with `openssl`), serving `mock/org.mjs` (an in-memory org: REST, Tooling, Bulk API 2.0, `frontdoor.jsp`, Lightning redirects, with request counts; users including another developer and Automated Process, Apex classes and a trigger, SOQL `LIKE`) and `mock/pages.mjs` (stand-ins for the classic pages with the same DOM ids, a record page with Edit/Save, Lightning Home and Setup). Anonymous Apex runs in `mock/apex.mjs`, a tiny interpreter that writes a real-looking log (including HTTP callouts: `new Http().send(req)` answers 200 and logs CALLOUT_* entries, plus NAMED_CREDENTIAL_* ones for `callout:` endpoints). `launchWithExtension({ mock })` starts Chrome with `--host-resolver-rules` mapping only `apexdbgr-mock.*` (`.my.salesforce.com`, `.lightning.force.com`, `.my.salesforce-setup.com`) to the server and every other host to nowhere, so nothing reaches a real org; mock ids follow the real id pattern (`005MK0…`). `org.delays` holds requests back (used to test the Lightning wait). The mock has an External Client App (`org.createJwtApp()`: a fresh key pair, `/services/oauth2/token` checking the RS256 signature, `iss`, `sub`, `aud` and `exp`), and a mock run logs in through it with the same `login()` as the real org (`mock.jwtEnv`). `lib/run.mjs` (`startRun()`) gives both scripts the session, the Node helper (`lib/salesforce.mjs`) and the browser for either mode, and counts Salesforce requests (`lib/request-counter.mjs`: Node fetches and every page's requests, by kind; the mock counts on the server too), printed at the end of a run and saved in the audit's `summary.json`. Against the real org, `loginReusingSession()` (`scripts/lib/sf-auth.mjs`) reuses a session (JWT bearer or SOAP) for 90 minutes between local runs (`.chrome-test/sf-session.json`, mode 600; not in CI or with `SF_SESSION_CACHE=0`), and the helper logs in once more after a 401.

Against the real org: `cd e2e && npm install && npm test` rebuilds the extension, then runs `apex-logs.test.mjs` (`node --test` + `puppeteer-core`, headless Chrome for Testing, throwaway profile; `HEADFUL=1` to watch). It logs in with `.env.local` (or `SF_ACCESS_TOKEN` + `SF_INSTANCE_URL`), makes sure the user has a trace flag (`ApexDbgrExtension` debug level, like the app), runs anonymous Apex with a unique marker, and finds the resulting ApexLog. It then checks both views:
- **Classic** (`/p/setup/layout/ApexDebugLogDetailEdit/d?apex_log_id=…`, `debug-log-page.ts`): marker visible and findable, every theme applied to every event class (colors and fonts), font size, and a debugged `<img onerror>` payload shown as text (collapsed and expanded) with no element created and no handler run.
- **React app** (opened with Shift+W, light mode, reduced motion): log listed, a log over 2.5 MB listed with no filter active, light-mode colors from the tokens, live search filters to the marker's log (and clears), the operation filter reloads only matching logs and shows a chip, Tab reaches a log row and Enter opens it, the delete dialog shows scope and counts and Cancel deletes nothing, the `?` overlay, log body visible, the `<img onerror>` payload shown as text, find in log counts and highlights matches, error lines have a marker, the Summary panel (the caught exception jumps to its line, "Number of SOQL queries" 4 / 100, the query run 3 times in a loop is one row with count 3 and the loop hint and jumps to each occurrence, and on the mock an insert of 2 accounts; on the mock a failed log opens with the summary shown and the Errors tab selected, and it stays hidden after the user hides it), the Call tree tab lists the anonymous code unit inside the execution with its SOQL count (on the mock also the method it called), opens and closes with arrows, and Enter goes to its line; the Timeline tab draws, zooms and a click on a bar goes to its line, every palette styles every line by its category (colors and fonts), custom color, font size, text wrap, dark mode (tokens and dark palette), a second long log (2500 debug lines, above `RENDER_ALL_UP_TO`) renders only the lines in view and every line in order when scrolled through, and Shift+W again focuses the open app instead of opening another. Controls are found by role, label or text (puppeteer `::-p-aria` and `::-p-xpath`), not by MUI class names.
- **Lightning:** switches the user to Lightning Experience for the test (`UserPreferencesLightningExperiencePreferred`, restored afterwards) and presses Shift+W on Lightning Home (`*.lightning.force.com`) and Lightning Setup (`*.my.salesforce-setup.com`); the app must get the `my.salesforce.com` session and list logs. `lib/lightning.mjs` (`gotoLightning`) waits for the Lightning domain and its shell (not network idle, which Lightning never reaches) and navigates once more if the frontdoor redirect takes too long.
- **Classic toolbar, list, options, page shortcuts:** the classic log page's toolbar (labels, sticky, timestamps without a reload, expand button names, "Match color mode"), the classic list's delete dialog (scope and count; Escape deletes nothing; no delete key) and search count, the options page (conflicts reported, save, restore defaults with confirmation and undo, shared color mode) and, on the mock only, Save on Ctrl/Cmd+S (a bare `s` does nothing) and turning page shortcuts off, and callouts (a callout run in the mock org: the Named Credential entries expand to one field per line in the app, with "Expand values", and on the classic page, and collapse back; the two-field CALLOUT_REQUEST/RESPONSE have no button).

Logs are found with `sf.findLogs([markers])`, one poll for all of them, each body downloaded once. At the end the run prints its Salesforce request counts.

`node large-log-perf.mjs` (in `e2e/`, not part of `npm test`) creates a ~20 MB log (or takes `--log <id>`), opens it in the app and prints the time to the first rendered line, DOM size, heap and scroll step times; `--ext <dir>` loads another build of `chrome/app` for comparisons.

Expected styles come from `react/src/core/log/themes.ts` and `categories.ts`, which `e2e/lib/styles.mjs` imports directly (Node strips the types; keep those two files free of runtime imports), so new themes are covered in both views automatically. `openAppWithShiftW()` records the messages content scripts send to the service worker: it presses Shift+W only after the page's `getShortcuts` request (when Mousetrap binds), with the tab in front and focus moved to the top document, and counts the press as handled when `focusAppTab` arrives. On failure it saves `e2e/artifacts/<name>.png/.log` (sid redacted) with the focus state, each press and the worker messages. Shared login code lives in `scripts/lib/sf-auth.mjs`. Page errors are reported as test diagnostics, not failures.

UX audit: `cd e2e && npm run ux-audit -- [--out <dir>] [--compare <previous dir>] [--mock]` (`e2e/ux-audit.mjs`, used by the `ux-ui-review` agent) captures every view (including the call tree and timeline, `exec`, with a pixel contrast check of the timeline canvas) at 1440×900 and 1024×768 with axe-core, contrast, control-name, keyboard and clipping checks into `e2e/ux-artifacts/` (gitignored). The baseline findings are in `docs/ux/baseline-review.md`.

CI: `ci.yml` runs the flow against the mock org (job `e2e-mock`) on every push and pull request. `.github/workflows/e2e.yml` runs the flow on pushes to `main`, same-repo pull requests and manual dispatch, using repository secrets `SF_USER`, `SF_CLIENT_ID`, `SF_JWT_KEY` (the PEM private key) and optional `SF_LOGIN_URL`, plus the optional second org `SF_USER_2`, `SF_CLIENT_ID_2`, `SF_JWT_KEY_2`, `SF_LOGIN_URL_2` (`SF_PASS`/`SF_TOKEN` and `_2` still feed the SOAP fallback until they're removed). Runs are serialized because they share one org. In CI (`CI` set) Chrome starts with `--no-sandbox`.

## Architecture

**Content scripts** (`react/src/extension/`, loaded from `js/build/` per URL pattern in `manifest.json`):
- `shortcuts.ts` (all Salesforce pages, Mousetrap): binds the user's page shortcuts (fetched via the service worker's `getShortcuts`, which answers `{ settings }`), and rebinds when they change (`chrome.storage.onChanged`). Shift+W opens the React app with `oid`/`uid` from the `disco` cookie and the session token in the URL. Ctrl/Cmd combinations (Save) also work in fields.
- **Page shortcut registry** (`core/page-shortcuts.ts`, no imports): the built-ins (open the app `w`, newest log `l`, Edit `Shift+E`, Save `Mod+S`) and navigation shortcuts (Shift+key in a new tab, Alt+Shift+key in this tab), `bindingsFor`, `validateShortcuts` (conflicts, invalid keys and paths, browser-reserved Ctrl/Cmd keys), `describePageShortcuts` (for lists), and the classic pages' own keys (`CLASSIC_LOG_PAGE_SHORTCUTS`, `CLASSIC_LOG_LIST_SHORTCUTS`). Saved in `chrome.storage.sync` `pageShortcuts` (`{ version: 2, enabled, shortcuts }`); `enabled: false` leaves only "Open Apex Debugger". 0.8.x's list (`shortcuts`) is migrated by `migrateLegacyShortcuts` (custom shortcuts and removed defaults kept; a new built-in whose key a user's shortcut already uses starts off), written once on install/update by the worker and left in place for a downgrade. No bare letter changes data.
- The classic-page scripts build their UI with `classic-ui.ts` (`h()` element builder, labeled `checkbox`/`select`, `injectDesignTokens()` = `designTokensCss('.ad-root')`, `followColorMode()` from `shared-appearance.ts`), styled by `chrome/app/css/classic.css` (every rule scoped to `.ad-root`). Controls on Salesforce's light pages (list, class list) are forced light; the log page's toolbar and log box, and the delete dialog, follow the color mode.
- `debug-log-page.ts`: enhances the classic single-log detail page, with the parsing in `core/log`: a sticky toolbar (`#adToolbar`: log colors with "Match color mode", font size, wrap, user/system methods, timestamps re-rendered without a reload, expand all, Open in Apex Debugger at `#/logs/<id>`, its shortcuts), the log box (`pre.ad-log`, a labeled region) with ID links and named expand buttons (USER_DEBUG and callout values, `core/log/values.ts`). Its settings stay in the Salesforce page's localStorage (`style`, `fontSize`, `showTimeStamp`, `apexDebugger.*`); the org's key prefixes are cached there for a day (`apexDebugger.keyPrefixes`).
- `debug-log-list.ts` and `class-page.ts` call Salesforce through `pageSalesforce()` like every content script.
- `debug-log-list.ts`: adds Load new logs, Logs per page, Add current user, "Delete logs…" and a body search with a result count and "Only matching logs" to the debug-log list page (`listApexTraces.apexp`), and opens the app for `?openApp=yes`. Delete opens a native `<dialog>` every time: only my logs (default) or all users', each with its count, a confirm button that names the count, progress and a result; it never falls back from "mine" to all (`deleteLogs` takes an explicit `LogScope` and refuses a user scope without a valid id). Search downloads each body once per page. Its keys (`l`, `/`, `c`) are on its own Mousetrap instance and follow the page-shortcuts switch.
- `class-page.ts`: "See all" buttons and a "Don't log (24 h)" checkbox per class (labeled with the class name), with a status line.

**Service worker** (`background.ts`): a message router keyed on `request.command` (`getToken`, `getShortcuts` (answers `{ settings }`, migrated if needed), `openTab`, `openOrFocusTab`, `focusAppTab`). `runtime.onInstalled` saves the migrated page shortcuts once. Tab ids for the options tab (`options_tab`) and each org's app tab (`app_<orgId>`) are kept in `chrome.storage.session`, since the worker's memory doesn't persist; `tabs.onRemoved` drops them. `focusAppTab` (sent by Shift+W with the org's tab name) focuses an open app tab and answers whether it did. It exposes `self.getSessionForUrl` for the e2e flow.

**Options page** (`extension/options.js`, `src/options/`, `html/options.html`, opened in a tab): React + MUI with the app's theme (`ui/themed.js`) and a store from `createPersistedStore(null)` (`settings-store.ts`, no Salesforce client). Sections: Appearance (the same `AppearanceSettings` component and settings as the app's panel; changes apply at once), Keyboard shortcuts (switch, table with key fields and their combinations, inline conflict and path errors, Add, explicit Save with status, Restore defaults behind a confirmation with Undo, read-only lists of the classic pages' and the app's keys), Session (advanced: the saved session id, with what storing it means).

**React app** (`react/src/`, opened as `html/app.html?oid=&uid=&sid=&host=`):
- `app.js` renders `LogsPage` (`pages/logs/logs.js`) with `createRoot`, inside the Redux `Provider` and MUI's `ThemeProvider` with `createAppTheme(mode)` (see Design system below); the color mode follows `prefers-color-scheme` unless the user picks one in Appearance.
- Layout: header (`components/app-header.js`: org host, `logging-control.js`, Refresh, `?`, overflow menu with Appearance… and Delete logs…), `filter-bar.js` (live search, filter chips, Filters popover, count), then the sortable `log-list.js` grid (one Tab stop, roving tabindex, arrows/j/k, Enter) or, with a log open, the compact list (collapsible to a rail) next to `log-viewer.js` (metadata, tabs Log / Call tree / Timeline, find with counter, next error/debug, Events toggles with counts, expand values, Summary). The Summary button opens `log-summary-panel.js` above the log body (a failed log opens with it shown; otherwise it stays as the user left it, not saved between sessions): tabs for errors, governor limits per namespace (bars amber at 70 %, red at 90 %), SOQL grouped by query text and DML by operation and object (sortable count, rows and time, a "possible … in loop" hint when a statement ran more than once from the same Apex line); each entry jumps to its line (a group to its next occurrence), showing its event type first if hidden. The model is `core/log/log-summary.ts` (`summarizeLog(lines)`, one pass, only parsed while the panel is open). Dialogs: `dialogs/appearance-panel.js` (drawer), `delete-logs-dialog.js` (scope only mine/all, counts, named confirm, progress), `shortcuts-dialog.js`, `trace-flags-dialog.js` ("Trace flags…" from the logging control: the org's active flags with expiry and a named Stop each; trace me, another user by name, Automated Process or an Apex class/trigger, with a debug level and a duration; nothing starts until "Start tracing"). Keyboard shortcuts are data in `core/app-shortcuts.ts` (bound by `use-app-shortcuts.js`, listed by the `?` overlay); none deletes anything. The app never starts logging by itself.
- `hash-route.ts`: the two screens are `#/` (log list) and `#/logs/<id>` (a log); `useOpenLogId()` follows `location.hash`, `openLog(id)` sets it.
- `global-sf.ts` builds the core Salesforce client from the URL query params (requests to `https://<host>` with the `sid` param as Bearer token, renewed from the service worker after a 401), plus `hostname`, `getUserId()` and `getOrgId()` (from `uid`/`oid`, or from `/services/oauth2/userinfo` when the opening page couldn't read them). `store.ts` (`configureStore`) passes it as the thunk extra argument, so thunks (`pages/logs/actions.ts`) get it as the third parameter: `(dispatch, getState, sf)`.
- Redux state is `{ logsPage }`, one slice (`pages/logs/logs-slice.ts`, `createSlice`) with all reducers and action creators. `settings-store.ts` (`createPersistedStore`) builds the store for the app (`store.ts`, with the client) and the options page: it saves settings on change, applies settings another extension page saved (`storage` events, `settingsLoaded`) and mirrors the color mode to `chrome.storage.local` `appearance` for the classic pages. `persisted-settings.ts` saves `maxLogs`, `sideLogsOpen`, `styleConfig` (`{ theme, colors, fontSize, textWrap }`), `hiddenCategories` and `colorMode` to the extension's **localStorage** (`apex-debugger.settings`, shared with the options page). Settings saved by 0.8.x in sessionStorage (`redux-localstorage`) are read once and migrated: old theme names map to the new palettes and only the colors the user edited are kept (`migrateSavedTheme`). List filters aren't persisted and none is active by default. Log bodies stay in memory (`logBodies`).
- Log body (`components/parsed-log.js`): split into the header plus one line per entry (`core/log/parsing.ts`), virtualized with `@tanstack/react-virtual` inside the log view's scrolling element; rows are `pre > div` with `data-index` (0 is the header), `data-category` and their measured height; each has a gutter (line number via CSS, error marker, expand toggle for USER_DEBUG and callout values, `core/log/values.ts`) and the entry text (time prefix muted). The line model (find matches, category counts, next error/debug, segments with ids and highlights) is in `core/log/log-lines.ts`. Logs with up to `RENDER_ALL_UP_TO` (2000) entries render every line, so the browser's find works; longer ones (up to 20 MB) render the lines in view plus an overscan. Per-line state (the value expand toggle) lives in `ParsedLog`, not in the rows, since rows unmount when scrolled away.
- Call tree and timeline: `core/log/execution-tree.ts` builds the execution tree from the log's lines (`buildExecutionTree`: execution, code units, methods, constructors, system methods, SOQL, SOSL, DML, callouts, flows, Visualforce, workflow; begin/end pairs in `UNIT_EVENTS`) with total and self time from the nanosecond timestamps and inclusive SOQL/DML counts. Unbalanced logs: an end closes the nearest open unit of its kind (by name first), units left open inside it end there, an end without a begin is ignored, and units still open at the end of a truncated log end at its last timestamp (`unclosed`). Iterative throughout (no recursion). The viewer builds it only when one of the two tabs is first shown and keeps both panels mounted once shown. `execution-tree-view.js` is an ARIA treeview (one Tab stop, `aria-activedescendant`, virtualized, only open units' children listed); `execution-timeline.js` is a canvas flame chart drawing only bars at least half a pixel wide (`timelineBars`), with zoom and pan; bars are filled with their category's palette color and labeled in the background color (so they keep the palette's 4.5:1), and its keys are in `core/app-shortcuts.ts` (groups Call tree and Timeline, listed by the `?` overlay and the options page). Tree rows are named by their own text plus `sr-only` column names; both tabs show a `StatePanel` for a log without units. Enter, a double click or the line link in the tree, or a click on a bar, goes back to the Log tab at that line (`rowForLine`, the next shown line if its category is hidden).
- Log line styling: the viewer sets `themeCssVariables(withCustomColors(paletteFor(styleConfig.theme, mode), styleConfig.colors))` on the log's scroll element; `parsed-log.js` styles `.cat-<category>` from those variables (the same variables the classic page uses).

**Design system** (shared by the app, the options page and the classic pages):
- `react/src/ui/tokens.ts` (no imports): color tokens for light and dark (`bg`, `surface`, `text`, `textMuted`, `border`, `accent`, `focus`, `danger`, match highlights, …), type scale (12/13/14/16/20), 8 px spacing, radius, layout sizes, focus ring. `tokenCssVariables(mode)` gives `--ad-*` custom properties; `designTokensCss(selector)` returns a stylesheet (light, dark under `prefers-color-scheme`, forced with `data-ad-color-mode`, and a `:focus-visible` ring) for content scripts to insert with `textContent`.
- `ui/contrast.ts` (no imports): WCAG contrast math and the thresholds (4.5:1 text, 7:1 errors and USER_DEBUG, 3:1 non-text). `tokens.test.ts` and `core/log/themes.test.ts` check every token pair and every palette category.
- `ui/theme.ts`: `createAppTheme(mode, reducedMotion)` builds the MUI theme from the tokens (dense, sentence-case buttons, visible focus, readable placeholders, no animations with `prefers-reduced-motion`). `ui/color-mode.js`: `useResolvedColorMode`, `useReducedMotion`. `ui/components/`: `IconAction` (icon button whose tooltip and aria-label match, with its shortcut), `StatePanel` (empty and error states), `Toast` (confirmations only, `role=status`), `Keys` (`<kbd>`).
- `ui/themed.js`: the MUI theme, CssBaseline and the tokens as `:root` variables for an extension page. `ui/components/shortcut-list.js`: a titled list of shortcuts (the `?` overlay, the options page).
- `core/salesforce/errors.ts`: `explainError()` turns failures into a plain-language cause and hint (session expired, no permission, unreachable).

**Log themes** (`core/log/themes.ts`): one list of palettes (`light`, `dark`, `monokai`, `high-contrast`) with a color, font weight and font style per category, a background and a muted color, used by both views. The app's and the classic page's default is `AUTO_THEME` (light or dark with the color mode); `DEFAULT_THEME` (`dark`) is the fallback for unknown names. Dropped themes (`emacs`, `bw`) resolve to `light`. Users' own colors are stored separately (`CustomColors`). The app reads the data directly; the classic page sets `themeCssVariables(theme)` (`--log-background`, `--log-<category>-color/-weight/-style`) on `#debugText` and the log box, and `css/debug.css` applies them to the category classes (`CLASSIC_CATEGORY_CLASS`; errors are `.err`, with a left border too). A new theme needs only an entry in `logThemes`.

**Salesforce data the extension creates:** user trace flags are `USER_DEBUG` with the `ApexDbgrExtension` debug level (all DEBUG), from now for 24 hours ("Start Logging" in the app, "Add Current User" on the classic list); if Salesforce refuses (an overlapping flag), the extension's own flags (also the older `ApexDebugger` level) are deleted and the flag is created without an expiration date. "Dont Log Class" on the class list sets a 24-hour `CLASS_TRACING` flag with the `ApexDbgrNoLog` level (all NONE). The app's "Trace flags" dialog (`setTraceFlag`) sets `USER_DEBUG` flags for users (also Automated Process, found by `UserType = 'AutomatedProcess'`) and `CLASS_TRACING` flags for classes and triggers, for 30 minutes to 24 hours; an entity's active flag of that type is updated (level and window) rather than duplicated. "Custom levels" are saved in the extension's `ApexDbgrCustom` debug level (updated each time, so flags already using it change too). Stop deletes that one flag. "Delete logs" (both views) is one Bulk API 2.0 delete job, for an explicit scope (`{ scope: 'user', userId }` or `{ scope: 'all' }`).

## Releasing

See "Releasing" in README.md. `scripts/version.sh patch|minor|major` bumps `chrome/app/manifest.json` (the source of truth for the version), commits and tags `vX.Y.Z`; `git push --follow-tags` runs `.github/workflows/release.yml`, which builds every script (they are not committed), zips `chrome/app` (no source maps), creates a GitHub release and calls `publish-chrome-web-store.yml` (Chrome Web Store API v2, keyless auth via workload identity federation, set up as in `docs/chrome-web-store-publishing.md`). Retry a failed upload with `gh workflow run publish-chrome-web-store.yml -f tag=vX.Y.Z`. The Salesforce API version is set in two places, kept equal: `react/src/core/salesforce/api-version.ts` (app and content scripts) and `API_VERSION` in `scripts/lib/sf-auth.mjs` (e2e). Any new remote host the app calls must be added to `content_security_policy.extension_pages` `connect-src` and to `host_permissions`.
